## Decisions and assumptions

- The named hardening branch is authoritative; creating it from the draft implementation commit was safer than modifying the forbidden production branch.
- Credential-like values are treated as compromised even if they were intended as demo keys. Repository sanitization is in scope; provider-side revocation is an external blocker.
- Demo fixtures are acceptable only when clearly labelled and never represented as live fraud intelligence.
- Release freshness uses the signed workflow run number as a canonical decimal high-water sequence. Equal sequences are always replays; the normal two-argument runner is forward-only; the exact third argument `--allow-rollback` is an exceptional operator path and never lowers the highest-ever accepted sequence.
- Deployment source freshness is independent of the signed sequence: the tested workflow-run SHA (or manual main SHA) must exactly match a fresh, strict `refs/heads/main` read before the only `tar|ssh` stream and a second fixed GitHub API read on the host after candidate validation, immediately before downtime. Network, HTTP, size, missing-ref, JSON, format, or mismatch failures stop ordinary deployment. The host request is deliberately unauthenticated and sends no secret.
- Deployment transport is fixed to `finguard-deploy` and `/home/finguard-deploy/finguard-deploy`. Host setup removes supplementary groups, locks password authentication, and owns the only passwordless sudo rule: the installed runner with the two exact forward-release paths. `--allow-rollback` remains available only to a separate direct/local root administrator and is rejected for the transport sudo identity.
- An ordinary HTTPS configuration refresh uses `https-config.sh --refresh-existing`: it makes no Certbot/network call, recovers exactly one lowercase domain from the active non-symlink site, requires canonical matching Let's Encrypt certificate directives/files, renders only the reviewed template, and preserves the old site until validation and reload succeed. Setup invokes the same helper when it detects an already-enabled TLS site; malformed or ambiguous TLS identity fails closed rather than reverting to plaintext bootstrap behavior.
- The deploy identity uses `/usr/local/libexec/finguard-deploy-transport` as both its configured shell and its `authorized_keys` forced command. Its sole key record begins with OpenSSH `restrict`, the home/key boundary is root-controlled, and only the staging directory is transport-writable. The dispatcher accepts only `finguard-deploy-activate-stream`, locks the staging directory inode before cleanup/receive, bounds and validates an isolated two-entry container, and invokes the existing exact two-argument sudo runner only after both fixed files are placed. Direct trusted local-root rollback remains outside this SSH identity.
- Browser and Android gates use local/demo data. No real UPI payment, report submission, contact message, paid AI request, push, merge, or deployment is authorized.
